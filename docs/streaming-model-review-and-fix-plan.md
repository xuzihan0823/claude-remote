## 2. 已确认的行为缺陷

### F-01：重连后运行状态无法恢复（已完成）

**代码位置**

- [App 重连恢复](../app/src/screens/ChatScreen.js)：`ws-open` 回调，约 208 行；运行状态判断约 339 行。
- [Web 重连恢复](../web/ui/screens/chat.js)：`ws-open` 回调，约 200 行；运行状态判断约 317 行。
- [服务端订阅处理](../packages/daemon/src/server.ts)：`#onClientFrame`，约 774 行，目前仅补发流草稿快照。

**触发过程与影响**

1. 页面收到 `run.started`，将 `runActive` 设为 `true`，保存 `activeRunId`。
2. WS 断开；运行在断线期间完成，页面错过 `run.done/error`。
3. 重连补拉拿到 `status: idle`，但只调用 `setStatus`。
4. `isRunning = runActive || status === 'daemon-driving'` 仍为 `true`，界面继续显示停止按钮或打字点，发送入口无法正常使用。

定向复现得到：`status === 'idle'`、`runActive === true`、`activeRunId` 仍指向已结束的运行。

**根因**

运行事实被拆成 `status`、`runActive`、`activeRunId`，实时事件与恢复请求没有统一更新这三者。订阅时不补发当前运行身份；重连逻辑还在本地消息为空时直接返回，跳过恢复。

**修复方案**

- 建立统一的运行状态应用入口，App 与 Web 使用相同规则；实时事件、首屏和重连快照均走此入口，避免只改其中一个字段。
- 为指定会话提供权威的当前状态与 `activeRunId` 快照，优先在指定会话 WS 订阅成功时发送。不要伪造新的 `run.started` 来表达快照，以免重复触发启动副作用。
- 快照显示无活跃 daemon run 时，清除旧 `runActive`、`activeRunId`；显示正在运行时同步真实 runId。
- 本地消息为空也必须恢复状态。不要依赖 `fetchSessions(200)` 一定能找到当前会话；旧会话可能不在前 200 条。
- 防止先发起的 HTTP 恢复响应覆盖后收到的启动/结束事件。给恢复请求加会话/连接有效性及事件先后保护，或使用同一 WS 中有序的状态快照。
- 发送 API 返回的 `runId` 应及时进入本地状态，不必完全依赖可能先于页面订阅到达的启动事件。

**验收条件（当前 App 与 daemon 自动化验证已完成；浏览器页面已移除，未执行真机交互）**

- [x] 断线期间结束后，权威快照复位运行标记、身份及草稿；覆盖正常完成和中止的 HTTP/WS 集成及 error 事件页面回归。
- [x] 断线期间仍在运行，重连后同步当前 runId，并恢复本轮草稿。
- [x] 空消息会话、首次加载失败后重连也能恢复；运行状态不依赖会话是否在前 200 条列表中。
- [x] 旧 HTTP 恢复响应不覆盖新运行状态，旧连接补拉不污染新连接。
- [x] App 和 App 共用 core 已覆盖；不恢复已移除的浏览器页面。

### F-02：过期停止请求会中止下一轮（已完成）

**代码位置**

- [App 停止操作](../app/src/components/composer/ChatComposer.js)：`stopRun`，约 48 行；错误分支约 59 行。
- [服务端停止路由及处理器](../packages/daemon/src/server.ts)：路由约 286 行，`#handleAbort` 约 470 行。
- [Web 停止操作](../web/ui/screens/chat.js)：停止请求及错误处理。

**触发过程与影响**

1. 会话运行 A，客户端提交 `{ "runId": "A" }` 的停止请求。
2. 请求延迟；A 已结束，运行 B 已开始。
3. 服务端忽略请求体，调用 `activeRunId(sessionId)` 得到 B，并停止 B。

已通过现有测试装配的真实 HTTP 服务复现：提交 A 的 runId，响应返回 B 的 runId 和 `status: aborted`。

**根因**

前端已携带运行身份，路由却没有读取请求体，处理器只按会话操作当前运行。与此同时，前端将所有 HTTP 409 都视作运行结束；若新增身份不匹配错误而不调整该分支，仍会把正在运行的 B 错误显示为空闲。

**已实施方案及最终契约**

`POST /api/sessions/:id/abort` 接受可选 `{ "runId": "<uuid>" }`，兼容已有无请求体和 `{}` 调用。

| 请求与状态 | 实施结果 | 必须保证 |
| --- | --- | --- |
| 指定 runId 等于当前 runId | `200 { runId, status: "aborted" }`，沿用现有命名 | 只中止指定运行；响应表示已接受，不代表清理已完成 |
| 指定 runId，当前无运行 | `200 { runId: null, status: "idle", sessionStatus }`，其中 sessionStatus 是真实会话状态 | 幂等；不得顺带解除 terminal-driving，也不得将其显示为空闲 |
| 指定 runId，与当前运行不同 | `409 { error: "run_mismatch", activeRunId, status: "daemon-driving" }` | 不中止当前运行 |
| runId 非字符串、空或非法 | `400 { error: "invalid_run_id" }` | 无状态副作用 |
| 未指定 runId，当前有运行 | 保留“停止该会话当前运行”的兼容行为 | 旧客户端仍可用，但不能获得指定轮次保护 |
| 未指定 runId，当前无运行 | 保留 `released` / `idle` 语义 | 不影响现有手动解除终端占用入口 |

- 读取、验证请求体后，在无异步间隙的同一操作中比对当前 runId 并调用 abort，避免校验和执行之间切换轮次。
- 客户端仅对明确的“无运行/已结束”结果清理状态；`run_mismatch` 应同步当前运行或重新取快照，不能调用无条件的 `onStopped`。
- 停止已接受时显示“正在停止”，通过对应终态或权威快照确认结束。现有 Runner 最长允许约 5 秒中止宽限，不应在 HTTP 一返回就宣称服务器已空闲。
- 迟到的 A 的停止响应或终态不得清除 B 的状态；前端按 runId 应用结果。
- F-01 的运行快照应保证中途进入和重连的客户端也能拿到真实 runId。无法获取 runId 的旧客户端保留兼容语义。

**验收条件（自动化验证已完成；未执行真机交互，见第 7 节）**

- [x] A 结束、B 开始后提交 A 的停止请求，B 继续执行且返回身份不匹配。
- [x] 同一 runId 重复停止、结束后重复停止均安全。
- [x] 非法 runId、坏 JSON 不改变运行或终端占用状态。
- [x] 无请求体及 `{}` 继续兼容，手动解除占用仍可使用。
- [x] 模拟 SDK 延迟中止及强制关闭期间，前端显示停止中，服务器仍拒绝并发发送。
- [x] 前端不会把 `run_mismatch` 或 A 的迟到结果解释为 B 已结束。

### F-03：HTTP 获取的正式消息没有参与草稿去重（已完成）

**代码位置**

- [App 消息合并](../app/src/screens/ChatScreen.js)：`addMsgs` 约 90 行；WS 去重约 154 行；首屏、resync、重连和分页调用处。
- [Web 消息合并](../web/ui/screens/chat.js)：`addMsgs`、`ws:message` 及 HTTP 获取路径。
- [共用草稿逻辑](../web/core/stream-drafts.js)：`applyStreamFrame` 与 `reconcileDrafts`。
- [服务端流快照](../packages/daemon/src/run/stream-buffer.ts)：`snapshot` 约 104 行。

**触发过程与影响**

页面持有草稿后断线，回答在断线期间写入 JSONL，页面错过正式消息和清除帧。重连通过 HTTP 拿到相同的正式回答，但没有执行 `reconcileDrafts`，两份文字同时显示。若旧清除帧已错过且不再有新事件，残留不会自行消失。

另一个必须覆盖的顺序是中途打开会话：服务端快照和首屏 HTTP 响应的先后不固定，已完成且已落盘的 block 仍可能经快照进入页面。

**根因**

草稿去重绑在 `ws:message` 单一路径，而正文事实上有多个入口。草稿晚于正文到达时也缺少对应检查。

**修复方案**

- 将正式消息合并与草稿消解放到统一入口，首屏、WS、重连、resync 和分页均使用。
- 即使消息已在 map 中，也应允许它参与草稿消解；不要因“没有新消息”提前跳过对账。
- 流快照到达时，也应对照当前有效正文，处理“正文先到、草稿后到”的顺序。
- 对账限定到当前会话和当前运行相关的消息，不要把整个历史按相同文本扫描后误删新一轮草稿。重复出现“好的”等短句必须有回归用例。
- 本阶段复用现有文本匹配时，保留其边界；若协议能提供稳定的 assistant message/block 身份，再使用身份对账，避免只凭前缀匹配。
- F-01 的快照确认无活跃运行后，取消旧清除计时器并清理残留草稿；仍在运行时保留本轮未落盘内容。
- `resync`、会话切换和运行切换时，使旧计时器及旧异步结果失效，防止清掉后续运行的新草稿。

**验收条件（App 与共用 core 自动化验证已完成；Web 已移除，未执行真机交互）**

- [x] 草稿后收到 WS 正文、HTTP 正文，均只显示一份。
- [x] 正文先到、流快照后到，仍只显示一份。
- [x] 同一内容重复补拉不导致重复或状态抖动。
- [x] 历史有相同短句时，新运行的流草稿仍正常显示。
- [x] 同轮多个 text block、工具调用间的多段回答保持顺序和正文完整。
- [x] A 的清除计时器不会清掉 B 的草稿；重连结束后无旧残留。

### F-04：失效模型的显示与发送值不一致

**代码位置**

- [App 模型选择器](../app/src/components/composer/ModelPicker.js)：约 19 行。
- [App 模型列表](../app/src/components/composer/ModelSheet.js)：选择状态和默认项。
- [Web 模型选择器](../web/ui/components/model-picker.js)：约 16 行。
- [已有会话发送](../app/src/components/composer/ChatComposer.js)：约 99 行。
- [新建会话发送](../app/src/lib/create-session.js)：约 13 行。
- [目录加载](../app/src/lib/useModelCatalog.js)、[目录校验](../packages/daemon/src/model-config.ts)。

**触发过程与影响**

选中模型 A 后，Mac 配置移除 A。目录刷新后，`findModel` 返回空，选择器将它显示为“默认 · B”；非空选择值 A 仍保留，发送时仍提交 A，服务端返回 `unknown_model`。目录尚未加载或切换到另一台设备时，也不能把“找不到”直接等同于“用户选择默认”。

**根因**

显示逻辑用“能否在目录找到”判定默认，发送逻辑用“值是否为空”判定默认；目录状态也没有区分加载中、失败和成功后确认为不可用。

**修复方案**

- 统一选择语义：只有空字符串表示跟随默认；非空但不可识别的值应显示原值及“待验证/不可用”，不能显示默认。
- 目录成功加载后，已移除模型建议保留可见的失效状态并阻止发送，提示重新选择；不要静默切到其他模型，避免费用和行为变化。
- 目录加载失败时，不应清空已有选择。无覆盖的默认发送继续按既有能力工作。
- 保留后端接受的内置别名兼容；模型不在 picker 行中不必然无效。前后端对“有效但目录无对应行”和“已移除具体 ID”作一致处理。
- 模型目录缓存绑定连接身份，切换设备时清理或隔离；新设备加载失败时不得将旧设备模型当作新设备目录。当前 App 切连接会清 sessionCache，但未清 modelCache。
- 已有会话 `unknown_model` 错误提供与新建会话一致的可操作提示，并刷新目录；不要自动重发。
- 明确选择器展示的是“下一条消息使用的选择”。运行中切换只影响后续发送，不调用当前 SDK 的 `setModel` 改变正在执行的轮次。

**验收条件**

- [ ] 模型被移除后不再显示默认，也不会无提示提交失效值。
- [ ] 用户选择跟随默认后，请求确实省略 `model`。
- [ ] 首次加载、加载失败、成功返回空目录分别有明确且一致的行为。
- [ ] 内置别名和完整 provider/model ID 的合法性保持兼容；同名不同 provider 不混淆。
- [ ] 切换设备或修改配置后，目录、显示和发送值一致。
- [ ] 运行中从 A 改选 B，不改变 A；下一次提交使用 B。

### F-05：默认模型设置没有同步到已挂载首页

**代码位置**

- [首页输入框](../app/src/components/composer/NewChatComposer.js)：`useState(() => getPref('defaultModel'))`，约 27 行。
- [默认模型设置页](../app/src/screens/settings/DefaultModelScreen.js)：`setPref`，约 15 行。
- [偏好订阅](../app/src/lib/prefs.js)：`prefs` 广播与 `usePref`，约 17 行。
- [导航](../app/src/App.js)：Home 在栈中保留，Settings 以 modal 展示。

**触发过程与影响**

首页先挂载并读取 A；进入设置页改为 B；返回首页，输入框的局部 state 仍为 A。即使父组件重新渲染，`useState` 初始化函数也不会重新执行，下一次新建仍提交 A。

**修复方案**

- 使用现有 `usePref('defaultModel')` 订阅偏好，避免再建一套偏好事件。
- 将全局默认值与当前新对话的临时覆盖分开：使用 `null` 表示“未作临时选择”，空字符串表示“显式选择跟随 Mac 默认”，非空字符串表示显式模型覆盖。
- 未作临时选择时随偏好变更；用户已为当前草稿显式选择模型时保留该选择，包括显式跟随默认。
- 创建成功后清除当前临时选择，让下一次新对话重新继承最新偏好；创建失败保留草稿、附件和选择。
- 发送开始时捕获有效模型，上传期间偏好变化不得改变已经发起的请求目标。

**验收条件**

- [ ] 首页保持挂载，设置从 A 改 B 后，新建请求使用 B。
- [ ] 当前草稿临时选择 C，再修改全局默认，当前请求仍使用 C。
- [ ] 当前草稿显式跟随默认时，偏好更新不会强行变成某具体模型。
- [ ] 成功创建后下一次新对话继承最新偏好；失败重试保持原选择。
- [ ] 附件上传期间修改偏好，不改变该次已发起请求的模型。

## 3. 相关问题与证据边界

### L-01：显示的默认模型不是指定项目的实际有效默认（已完成）

[模型目录](../packages/daemon/src/model-config.ts) 仅读取用户 settings.json；[SDK 桥接](../packages/agent-bridge/src/sdk-bridge.ts) 不指定 `settingSources`。本次已核对安装的 `@anthropic-ai/claude-agent-sdk@0.3.212` 类型文档：省略该选项会加载 user、project 和 local 三类配置。

因此用户配置显示 A、项目配置覆盖 B 时，当前默认项的“当前 A”不能保证等于实际执行模型。已确认的是配置来源不同，没有通过真实推理证明某个个人项目当前发生了偏差，也没有认定 SDK 不加载用户设置。

**已实施**：默认按钮、模型列表与设置页统一显示“跟随项目默认”；说明文案为“用户配置默认：A；实际运行遵循当前项目配置”。设置页页脚可换行，避免长模型名挤掉项目配置说明。没有读取到用户默认时也不虚构默认值。没有将用户模型强行注入 SDK；省略 `model` 的行为保持不变。

## 7. F-02 / F-03 实施记录

实施范围为 daemon、React Native App 和 App 使用的 `web/core`；不恢复浏览器页面，不提交、部署或重启服务。

### 最终接口与行为

- `POST /api/sessions/:id/abort` 读取并校验可选 UUID `runId`。不匹配返回 `409 { error: "run_mismatch", activeRunId, status: "daemon-driving" }`，当前运行继续；非法 runId 返回 `invalid_run_id`，坏 JSON 返回 `invalid_json`，均无状态副作用。
- 指定 runId 且当前无 daemon 运行，返回 `200 { runId: null, status: "idle", sessionStatus }`，不会解除真实终端占用。无请求体及 `{}` 保留停止当前运行、手动解除占用的兼容行为。
- `status: "aborted"` 只表示停止已受理。App 显示停止中并保持发送受限，等待运行终态；迟到响应、通用 404/409 不会被解释为新运行已结束。`run_mismatch` 仅在原请求上下文仍有效时同步服务端运行。
- 指定会话订阅成功后，WS 先发送 `{ type: "session-state", sessionId, status, activeRunId }`，再补流草稿。新会话尚未落盘时也发送该状态；全局 `*` 订阅不发送该帧。App 用无活跃运行的快照清理旧草稿，HTTP 状态恢复不覆盖后到的实时运行事件。
- 转录 assistant 消息存在 `message.id` 时，HTTP/WS 渲染消息携带可选 `apiMessageId`。Claude Code 落盘时一行只放一个 block，转录 `blockIndex` 多为 0，与流草稿 key 中的 SDK 下标不一致，因此 `apiMessageId` 只用于把对账限定在同一条 API 消息内，块仍按文本匹配（key 与文本都一致时优先）。旧数据无身份字段时，使用受当前轮次范围约束的原文本规则。
- 首屏、WS 正文、重连、resync 和分页都通过 `addMsgs` 消解草稿；流快照到达也检查已有正文。重复补拉仍对账，工具结果不切断当前轮次。运行切换取消旧清除计时器；清除计时器只移除已捕获的 key。会话切换和 resync 使旧 HTTP 响应失效。
